# 0005 — HTTP

## Problem

A step is an arbitrary `Action`, so a load test against a web service is the
user's own `HttpClient`, their own timing, their own idea of what counts as a
failure. Everyone writes the same forty lines, and each version disagrees about
whether a 500 is a failed request or a successful measurement of an error page.

## Not doing

- No third-party client. `java.net.http` ships with the JDK and works with
  virtual threads; a Ktor or OkHttp module can come later if anyone wants one.
- No response body assertions beyond status. Checks are a later spec.
- No cookies, no redirects-by-default, no auth flows.
- No connection warm-up. It changes what is measured; it needs its own spec.
- No streaming or file upload.

## Shape

```kotlin
import io.github.matthewjones372.proofload.http.http
import io.github.matthewjones372.proofload.scenario
import io.github.matthewjones372.proofload.sessionKey

val orderId = sessionKey<String>("orderId")

val checkout = scenario("checkout") {
    exec(http.get("/products"))
    exec("pay") {
        http.post("/orders")
            .header("content-type", "application/json")
            .body("""{"cart":"1 anvil"}""")
            .expecting(201)
            .capture(orderId) { response -> response.header("location") }
            .send(this)
    }
}
```

- `proofload-http`, depending on `proofload-core` and the JDK only, with its own
  `NoThirdPartyDependenciesTest`.
- `HttpAction` — an `Action` built from method, path template, headers, body.
- The **step name defaults to the path template**, never the substituted URL,
  so `/orders/{id}` stays one row in a report.
- `expecting(status)` — anything else calls `fail("status $actual")`.
- A transport error fails the step with the exception's class name.
- One `HttpClient` shared by the run, built for HTTP/1.1 and HTTP/2, with
  connection reuse on.

## Why this shape

The status check belongs in the action rather than in the caller's step body,
because "what counted as a failure" is the single most important thing a report
has to be consistent about. A default of `expecting(200)` and an explicit
override reads better than every user inventing the same `if`.

The path template as the row key is the difference between a report with eight
rows and a report with eighty thousand. It also means a load test written
against a real service names the endpoints the service's own docs name.

A shared client is right for a load generator: a client per user measures TLS
handshakes and connection setup, which is a different experiment from the one
almost anyone means to run. Where that is the experiment, it needs saying out
loud, so it is a later spec rather than a flag nobody reads.

## Stack

- [ ] **`spec-0005-module`** — the module, its wiring, its dependency test, and
      `http.get(path)` producing an `Action` that sends and records a status.
      Done when: a `get` against a local `HttpServer` returns `Ok`, a 500
      returns `Failed("status 500")`, and `./gradlew build` is green.
- [ ] **`spec-0005-request`** — headers, body, `expecting`, method coverage,
      and the base URL.
      Done when: a POST with a body and a 201 expectation passes, and the same
      request against a 200 fails naming the status it got.
- [ ] **`spec-0005-session`** — path templates filled from session keys, and
      `capture` writing a response value back into the session.
      Done when: `/orders/{id}` fills from a session key, and the step's
      recorded name is still `/orders/{id}`.

```bash
./gradlew spotlessApply && ./gradlew build
```

## Open questions

Answered by the architect:

1. **Tests run against `com.sun.net.httpserver.HttpServer`**, which is in the
    JDK. No test container, no third-party stub, no network.
2. **A request timeout defaults to 30 seconds**, and a timeout is a failure
    reason of its own rather than an exception class name.
3. **Redirects are not followed by default.** A 302 that a test did not expect
    is a finding, not a detour to be silently taken.
