# 0029 — Cutting 0.1.0

## Problem

Nothing is released. The build can publish — the Central Portal is configured,
signing is wired, the `.api` dumps are checked on every build — and no version
has ever been cut, so none of it has been proved. A publishing pipeline that
has never run is a pipeline that does not work.

The API has also moved four times in two days under review, which is the right
reason not to have released yet and the wrong reason to keep waiting forever.

## Not doing

- No 1.0. This is 0.1.0, and `CHANGELOG.md` already says that until 1.0 a break
  comes without a major bump.
- No API freeze. The `.api` dumps record the surface; they do not promise it.
- No announcement, no website, no Slack. A tag and a released artifact.
- No new features. Anything not already merged waits for 0.2.0.

## Shape

```bash
git tag v0.1.0 && git push --tags
```

The build reads the nearest `v` tag, so that is the whole release. What has to
be true first:

- **Every published module resolves from Maven Central**, installed into an
  empty project that depends on nothing else.
- **`docs/modules.md` exists** and matches what is published — spec 0027.
- **The README example compiles against the published artifacts**, not against
  the source tree.
- **`CHANGELOG.md` has a 0.1.0 section** with the caveats: the closed model is
  missing, the timeline is missing, and coordinated omission is handled but
  `behind` should be read before any percentile.

## Why this shape

A release proves the parts nobody tests: that the POM is right, that the
sources and javadoc jars are there, that the signature verifies, and that a
consumer with an empty `build.gradle.kts` can actually use this. Those fail
quietly and are found by a stranger otherwise.

0.1.0 rather than 0.0.1 because the thing works end to end and says so; and
because a version that signals "not really" gets treated as not really.

## Stack

- [ ] **`spec-0029-consumer`** — a smoke project that depends on the published
      coordinates and runs one load test.
      Done when: `publishToMavenLocal` plus the smoke project is green, from a
      directory that is not this repository.
- [ ] **`spec-0029-changelog`** — the 0.1.0 section, with what is missing
      stated as plainly as what is there.
      Done when: a reader can tell from the changelog whether this tool does
      what they need.
- [ ] **`spec-0029-tag`** — the tag, the staged bundle, and the release.
      Done when: the artifacts are on Central and the smoke project resolves
      them from there rather than from a local repository.

## Acceptance

```bash
./gradlew spotlessApply && ./gradlew build
./gradlew publishToMavenLocal
```

## Open questions

Answered by the architect:

1. **The staged bundle is inspected before release.** `gradle.properties`
    already leaves it staged rather than auto-releasing, and this is the run
    that proves why that default was chosen.
2. **The smoke project lives in this repository** but is not a module: it has
    its own settings file and resolves from a repository, because a composite
    build would test the source tree and prove nothing.
3. **Java 21 is the floor** and the POM says so. The toolchain already compiles
    against 21; the release is where that becomes a promise.
